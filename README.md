# Wind Forecast Intelligence

Replay any day in January 2026 as a GB day-ahead trader would have seen it: which national wind
forecast was available at the decision time, what actually happened, and how far off it was.

The backend answers two questions using Elexon data only:

1. **What was the latest wind forecast available when the purchase decision was made?**
   (`GET /api/v1/wind-analysis`)
2. **How accurate were those forecasts, quantitatively?** (`GET /api/v1/accuracy-summary`)

It does not estimate how much power to buy; it provides the wind input to that decision and its
measured error.

## Getting started

**With Docker** (only Docker needed):

```bash
docker compose up --build api                         # live Elexon data
SOURCE_MODE=fixtures docker compose up --build api    # recorded data, works offline
```

**Without Docker** (Python 3.12 and [uv](https://docs.astral.sh/uv/)):

```bash
make setup     # install dependencies
make dev       # API on http://localhost:8000 with live data
make ci        # lint, type check and the full test suite
```

Try it:

```bash
curl "http://localhost:8000/api/v1/wind-analysis?deliveryDate=2026-01-16"
curl "http://localhost:8000/api/v1/wind-analysis?deliveryDate=2026-01-16&cutoffDayOffset=-1&cutoffLocalTime=12:00"
curl "http://localhost:8000/api/v1/accuracy-summary"
curl "http://localhost:8000/api/v1/forecast-versions?deliveryDate=2026-01-16"
curl -OJ "http://localhost:8000/api/v1/wind-analysis/export?deliveryDate=2026-01-16"
```

## API

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/wind-analysis?deliveryDate=YYYY-MM-DD` | One delivery day replayed at a decision time: per-half-hour forecast vs actual, MAE/RMSE/bias, coverage, warnings |
| `GET /api/v1/wind-analysis/export` | The same replay as a CSV file, one row per half-hour |
| `GET /api/v1/forecast-versions?deliveryDate=YYYY-MM-DD` | Every forecast version covering a day, hour by hour, to show how the forecast evolved |
| `GET /api/v1/accuracy-summary` | Accuracy pooled over a window (default: decisions made in January), error distribution, best/worst days |
| `GET /api/v1/metadata` | Supported dates, decision-time presets, units, policies, metric definitions |
| `GET /api/v1/health/live`, `/health/ready` | Liveness and readiness |

The decision time is either an exact instant (`decisionCutoff=2026-01-15T09:00:00Z`) or a rule
relative to the delivery day (`cutoffDayOffset=-1&cutoffLocalTime=09:00`); without either, the
default (09:00 UK time the day before) is applied and echoed back. Each analysis carries a
`resultHash`, so two people can confirm they are looking at identical results. Every field, status,
warning and error code is specified in [`contracts/openapi.yaml`](contracts/openapi.yaml).

## How the analysis works

- **Data.** Actuals come from Elexon FUELHH filtered to `fuelType = WIND` (half-hourly, MW
  averaged over each 30 minutes). Forecasts come from Elexon WINDFOR, which publishes about eight
  versions ("vintages") a day, each an hourly forecast for the next ~3 days.
- **What was knowable.** For each hour, only forecasts published at or before the decision time
  are eligible (a forecast published exactly at the cutoff counts); the latest one is used. If
  several records share that latest publish time with different values, the hour is excluded
  rather than guessed. An older forecast is never used as a fallback.
- **Hourly forecasts, half-hourly actuals.** Each hourly forecast applies to both half-hour
  settlement periods of its hour, the way an hourly day-ahead product delivers constant MW. It
  barely affects the result: matching only the half-hours that start on the hour changes January's
  MAE from 2,042 to 2,022 MW, and the summary reports that figure alongside.
- **Error and metrics.** Error = forecast − actual, so positive means the forecast was too high.
  MAE, RMSE and bias are calculated from matched half-hours only, without rounding; missing or
  unusable values are excluded and counted, never treated as zero. With nothing to compare,
  metrics are `null`.
- **Time.** All comparisons use UTC. Delivery days are GB settlement days in UK local time, so
  clock-change days have 46 or 50 half-hours.
- **Default decision time.** 09:00 UK time on the day before delivery, just before the GB
  day-ahead auctions close. It is a default, not a market rule; other times can be chosen.

What the January 2026 data shows (decisions made in January, decision time 09:00 the day before):
the forecast was too high in 85% of half-hours, by 1.7 GW on average (MAE 2,042 MW), and in 9 of 10
half-hours the miss was at most 4,145 MW. On 15 January the 11:30 forecast was published late, at
12:25, so a noon decision that day relied on the 09:30 forecast.

## Testing

`make ci` runs everything CI runs. The suite covers:

- **Unit tests** for parsing, time handling (including both 2026 clock changes), forecast
  selection, status rules and metrics.
- **Property tests** (Hypothesis): a forecast published after the decision time is never used,
  the newest eligible forecast always wins, a later decision time never picks an older forecast,
  and input order never matters.
- **Recorded-data scenarios** with exact expected values, cross-checked against a separate, naive
  implementation over every day of January.
- **API tests** for every endpoint and error code, with each response validated against
  `contracts/openapi.yaml`.
- **Fixture checks** that the frontend's mock data matches the contract and the current backend.

`make traceability` runs the suite and lists each SRS requirement with the tests that cover it.
`make live` checks against the real Elexon API that the data still has the shape, hourly
resolution and history the service relies on; CI runs it daily.

## Configuration

Settings come from environment variables; see [`backend/.env.example`](backend/.env.example). No
secrets are needed. The most useful ones:

| Variable | Default | Meaning |
|---|---|---|
| `SOURCE_MODE` | `http` | `http` for live Elexon data, `fixtures` for recorded data (not allowed in production) |
| `CACHE_ENABLED` / `CACHE_TTL_S` | `true` / `21600` | In-memory cache of Elexon responses |
| `DEFAULT_CUTOFF_DAY_OFFSET` / `DEFAULT_CUTOFF_LOCAL_TIME` | `-1` / `09:00` | Default decision time |
| `SUPPORTED_DATE_FROM` / `SUPPORTED_DATE_TO` | `2026-01-01` / `2026-02-01` | Delivery dates that can be analysed |

## Design notes

- **Contract first.** `contracts/openapi.yaml` was written before the code so frontend and backend
  could be built in parallel; tests keep both sides honest.
- **Pure analysis core.** The `analysis` package does no I/O, which keeps the rules easy to test
  exhaustively. Services depend on a small `DataSource` interface, so the Elexon client, recorded
  data and the cache are interchangeable.
- **Fail loudly.** Every analysis is checked against the contract's guarantees (counts add up, no
  forecast published after the cutoff was used, RMSE ≥ MAE ≥ |bias|) before it is returned.
- **Caching.** Responses are cacheable by URL, and Elexon responses are cached in memory, so
  changing the decision time for the same day costs milliseconds.

## Limitations

- Only GB national wind, January 2026 (plus 1 February, the last day decided in January).
- WINDFOR does not document whether an hourly value is an average or a point value; the results
  are insensitive to this (see above), but the mapping is a stated assumption.
- Causes of the systematic over-forecasting (for example curtailment, or differences in which wind
  farms each dataset covers) are not assessed.
